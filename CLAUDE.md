# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

A GitHub Pages site (custom domain `https://linux-player.theirlnetwork.com`) that serves everything a fleet of Raspberry Pi kiosk devices needs: the guide website (`index.html`), the installer (`install.sh`), the uninstaller (`uninstall.sh`), and the `.deb` packages (`packages/`). The fleet is mostly CM5 devices with some Pi 5s — lead with CM5 in user-facing docs.

**Secrets policy — read before touching anything credential-shaped.** This repo is fully public (Pages serves every committed file). No credential, token, or password may ever be committed — not even "encrypted with the key nearby" (that was tried and rotated away; the old blob still sits in git history). The gateway's MQTT credentials live ONLY in the self-hosted config panel (see "IRL Gateway" below). The player's CMS device token is never committed either — devices resolve it at runtime and report it straight to the panel (see "Telemetry" below).

**`main` is production.** Every push to `main` redeploys the website (`.github/workflows/deploy-pages.yml`), and — because deployed devices re-fetch `install.sh` hourly and reinstall on any change — **any edit to `install.sh` merged to `main` rolls out to every device in the field within the hour**. There is no staging environment. Do work on a branch and PR into `main`.

## Commands

```bash
bash -n install.sh uninstall.sh   # syntax check
sudo bash tests/run-e2e.sh        # full test suite (~120 checks), must run as root
```

The e2e suite runs the real scripts inside a fake root under `/tmp` (system paths are sed-redirected, `systemctl`/`apt-get`/`dpkg`/`useradd`/`userdel`/`loginctl`/`pkill` are PATH-stubbed, a local `python3 -m http.server` plays GitHub Pages, the config panel, and the player's ad-server status endpoint). It makes no changes to the host. It covers: fresh install, all `irl-update` paths (no-op, changed script, captive portal, flock, canary gating), deleted-service propagation, real-time freeze- and network-watchdog simulations including the static-page brake and the netwatch never-reboot/outage-recording behavior (take ~90 s), the gateway config fetch (plus a no-credential-in-installer assertion), the telemetry snapshot and device-token resolution, the panel command channel (run-once, ack, re-send tolerance, bad-id/verb rejection), the weekly-reboot offline skip, the update-timer `Persistent=` guard, and uninstall. CI runs it on every PR. **Extend it whenever you add a service or change updater/watchdog/gateway/telemetry logic.** External URLs are sed-redirected to the local server — tests must never hit the real config panel or ad server.

To visually verify `index.html`, serve the repo (`python3 -m http.server`) and render with Playwright's Chromium at `/opt/pw-browsers/chromium` — the footer's dynamic version text only appears when the page is served over HTTP, not from `file://`.

## Architecture — how the fleet stays in sync

`install.sh` is the single source of truth for the entire device state. The chain:

1. **Auto-update**: `install.sh` installs `/usr/local/bin/irl-update` + `irl-player-update.timer` (hourly + on boot). `irl-update` fetches the published `install.sh`, compares its SHA-256 to the hash recorded at install time (`/etc/irl-player/installer.sha256`), and re-runs the script on any difference. Consequences:
   - Any change to `install.sh` = automatic fleet rollout (and a brief player restart per device).
   - **Failure reporting (rev ≥ 32)**: `install.sh` runs with `set -E` and an `ERR` trap (and `die()` does the same) that writes `/var/lib/irl-player/last-update-error` as `<epoch> rev <N> line <L>: <cmd>`; a run that reaches the end stamps `/var/lib/irl-player/last-update-ok` and deletes the error file. `irl-update` clears the error file before each attempt, writes a generic `rev ? reinstall exited <rc>` if a failed attempt left none (syntax error, killed), never advances the stored hash on failure (so it retries hourly), and starts `irl-player-telemetry.service` after every outcome so the panel hears within seconds. Telemetry carries them as `last_update_ok_at`, `last_update_error_at`, `last_update_error` (see 7). Best-effort lines (`cmd || log …`) never trip the trap. A first install that fails before telemetry exists can only be seen on the terminal. **Warnings (rev ≥ 35)**: a tolerated step whose failure still degrades the device (optional packages like grim/wlr-randr/unclutter/unattended-upgrades, the gateway venv + pip deps, the apt-daily timers, the `enable --now` of the gateway/telemetry/screen/reboot units) uses `warn "…"` instead of `|| log`: it logs AND appends one line to `/var/lib/irl-player/last-update-warnings` (cleared at the start of every run), which telemetry sends as `last_update_warnings` (list, `[]` when clean, ≤20 lines of ≤200 chars). A run with warnings still stamps `last-update-ok` — the panel should show it as degraded, not failed. Use `warn` for any new tolerated-but-degrading step; keep `|| true` / `|| log` for the cosmetic ones — and never for something that fails on every device (rev 36 lesson: `xcursor-transparent-theme` does not exist on current Raspberry Pi OS, so its rev 35 warning fired on the canary's first run and would have marked the whole fleet degraded forever; unclutter hides the cursor anyway). When checking a device after a rollout, `installer.sha256` is written by the installer *mid-run* — the run is only done when `last-update-ok` is newer than the trigger and `update-in-progress` is gone. **Interrupted runs (rev ≥ 35)**: `irl-update` writes `/var/lib/irl-player/update-in-progress` before running the installer and removes it when it returns; a marker found on the next check (with the lock held, so nobody is mid-install) means a reboot/power loss/kill mid-run and is recorded as `rev ? reinstall interrupted` unless an error is already on file. The retry that follows in the same run supersedes it.
   - `irl-update`'s body lives in `main()` **on purpose**: the reinstall overwrites the running script, and bash executes garbage if a running script's file changes under it. Keep that wrapper.
2. **Deletion propagation**: `MANAGED_FILES` (top of `install.sh`) lists every file the installer creates; the previous install's copy is stored in `/etc/irl-player/manifest`. On each run, files in the old manifest but not in the current `MANAGED_FILES` are `systemctl disable --now`-ed and deleted. **When adding or removing an installer-created file, update `MANAGED_FILES`, `uninstall.sh`, and the e2e suite together.**
3. **Canary rollout**: devices without `/etc/irl-player/canary` defer a new `install.sh` by `FLEET_DELAY_HOURS` (top of `install.sh`; `irl-update` parses the value out of the **newly fetched** script with `^FLEET_DELAY_HOURS=(\d+)$` — don't change that line's format). A canary-marked device applies immediately; publishing with `FLEET_DELAY_HOURS=0` makes the whole fleet apply immediately (urgent fixes). The pending wait is tracked in `/etc/irl-player/pending-update` (hash + first-seen epoch).
4. **Self-healing**: `irl-watchdog` hashes a `grim` screenshot every 30 s; a pixel-identical screen for 5 min = frozen → restart the kiosk service (max 3, counter clears only after 5 min of continuously changing screen) → reboot (max once per 2 h, timestamp in `/var/lib/irl-player/`). Static-page brake (rev ≥ 27): the hash it rebooted for is saved in `/var/lib/irl-player/last-reboot-hash`; if the post-reboot screen is pixel-identical to it, the picture is a static page a reboot can't cure (the pairing QR), and reboots slow to once a day (restarts continue). It deliberately does nothing when the screen can't be captured or the kiosk is intentionally stopped. `irl-netwatch` covers connectivity: 10 min offline → restart networking, then again every 30 min until back. **It never reboots (rev ≥ 29)** — product decision: an offline screen keeps looping its cached ads and only the community manager may reboot it (panel button, delivered via telemetry, see 7). It records the outage instead: `/var/lib/irl-player/offline-since` while offline, `/var/lib/irl-player/last-offline` (`<start> <end>`) once back, which telemetry reports. `irl-netwatch --online` runs the connectivity check once (exit 0/1) and gates the weekly reboot (8). `/etc/systemd/system.conf.d/irl-watchdog.conf` arms the Pi's hardware watchdog for full-OS hangs.
5. **OS updates**: `unattended-upgrades` (config in `/etc/apt/apt.conf.d/52irl-*` and `60irl-*`) applies security updates nightly with **`irl-player` blacklisted** — apt must never upgrade the app; only `irl-update` does. `AutocleanInterval "7"` prunes downloaded .debs weekly, and `/etc/systemd/journald.conf.d/irl-player.conf` makes the journal **persistent** (rev ≥ 33: `Storage=persistent`, `/var/log/journal` created, `journalctl --flush` so the running daemon switches to disk without a restart — a Lite image otherwise logs to RAM and loses everything at reboot) and caps it at 100 MB in 16 MB files (the installer runs `journalctl --vacuum-size` instead of restarting journald — a journald restart can wedge running services' stdout streams) — both keep the 16 GB eMMC from silting up over years.
6. **IRL Gateway** (`/opt/irl-gateway/`, service `irl-gateway`): bridges a USB-attached ESP32 master board (and its worker fleet) to MQTT. `gateway.py` is embedded in `install.sh` (source of truth: the `irl-microcontroller` repo) with a venv (`pyserial`, `paho-mqtt>=2.0` — newer than apt's). Its MQTT config is **fetched, never shipped**: `ExecStartPre` runs `irl-gateway-config`, which GETs `https://iot-config.theirlnetwork.com/mqtt-config?serial=<hw serial>` — the user's self-hosted config panel (Django + Docker Compose; source and docs in the `irl-microcontroller` repo, `config-panel/`; web UI for approve/reject/rotate). The endpoint contract is sacred: 200+JSON for approved, `403 not approved` for pending/rejected, `503 no config` for approved-without-config — devices know nothing else, and the client treats every non-200 the same (keep cached config, else retry). The JSON is written to `mqtt.json` **verbatim** (unknown keys pass through — keep it that way). If the config carries the panel's optional `tls_ca_pem` (inline PEM, injected when the operator uploads a broker CA), the gateway materializes it to `/opt/irl-gateway/config-ca.pem` and pins it for TLS, beating `tls_ca`; the installer never touches `config-ca.pem` (runtime state, like `mqtt.json`), and `uninstall.sh` removes it with the rest of `/opt/irl-gateway`. Note `tls_insecure` only skips the hostname check — it does NOT bypass a wrong pinned CA. Unknown serials auto-register as pending in the panel; unapproved/no-cache devices retry ~1/min (that retry IS the approval request). Approved devices keep the fetched `mqtt.json` (root-only) as an offline cache; `RuntimeMaxSec=1d` restarts the gateway daily so rotations/approvals propagate within a day. Devices without an ESP32 attached idle harmlessly. (A retired Cloudflare Worker at `config.theirlnetwork.com` preceded the panel — see git history.)

7. **Telemetry + CMS device token + command channel** (`/usr/local/bin/irl-telemetry`, `irl-player-telemetry.timer`, on boot + every 5 min since rev 29; was hourly): each run POSTs a device-health snapshot (identity, versions, health, wifi) to `https://iot-config.theirlnetwork.com/telemetry`, keyed by hardware serial, so the whole fleet is visible in the config panel. Fire-and-forget — a failed post affects nothing. It also reports the player's CMS **device token**, which is NOT stored on disk: it's re-resolved fresh every run the way the player does it — read `device_id` from the Flutter app's `shared_preferences.json` and `API_URL` from the bundled `/opt/irl-player/data/flutter_assets/.env`, then `GET $API_URL/api/v1/status/<device_id>` → `external_id`. So `device_id` (device-generated pairing UUID; public, stable, in the QR code) and `device_token` (`external_id`; CMS-issued credential sent as the `X-Device-Token` header; rotatable) are **different things** — the token is a live credential that travels only device→panel over HTTPS and is never committed here. Re-fetched every run, so rotations show up within minutes. On non-Pi hosts the serial is empty and `irl-telemetry` exits early (see the x86 note under "Releasing"). Snapshot fields arrive rev-gated: the panel stores only fields it knows and keys behavior off `installer_rev` (identity fields came with rev ≥ 21). Rev ≥ 25 adds the power/health extras for the panel's health page — `throttled_flags` (the `vcgencmd get_throttled` bitmask decoded to booleans `under_voltage_now`, `freq_capped_now`, `throttled_now`, `under_voltage_occurred`, `throttled_occurred`; `null` where `vcgencmd` is missing or fails) and `disk_free_pct` (root-fs free %, one decimal). Every field is nullable, and the panel must treat null/missing as unknown — never blanking a stored value. Note `mem_free_mb` has always been `/proc/meminfo` `MemAvailable` (despite the name) — the health page should read it rather than expect a new memory field. **Telemetry HMAC signing** (rev ≥ 25, panel contract in `config-panel/README.md` of the `irl-microcontroller` repo): the panel hands approved devices a per-device secret as the additive `telemetry_hmac` key (64 lowercase hex = 32 bytes) in the gateway's fetched `mqtt.json`; when present, `irl-telemetry` sends `X-IRL-Timestamp` (unix seconds) and `X-IRL-Signature` = lowercase-hex HMAC-SHA256 over `"<ts>." + <exact body bytes>`. No secret → unsigned post (pending devices; panel accepts it). The signed body must be byte-identical to the transmitted body — never re-serialize between signing and sending. Rotation needs no device change (secret re-read from `mqtt.json` every run; panel keeps a grace window). **Rev ≥ 29 (offline policy):** the panel calls a device down after 15 silent minutes (3 missed posts). New nullable fields: `boot_time` (epoch, now − uptime), `last_offline_start` / `last_offline_end` (epoch window of the last outage netwatch saw, from `/var/lib/irl-player/last-offline`), and `acked_commands` (list, always present). **Commands:** the panel's 200 response may be `{"commands": [{"id", "type": "reboot" | "restart-kiosk"}]}` (community-manager buttons). `irl-telemetry` runs each id exactly once — executed ids are kept in `/var/lib/irl-player/commands-done` (last 200; a re-sent id is skipped), pending acks in `/var/lib/irl-player/command-acks` (sent as `acked_commands` on the next post, dropped once that post is delivered). The panel re-sends until acked or expired (24 h). Ids must match `[A-Za-z0-9_.:-]{1,64}`; only those two verbs exist and a reboot always runs last. A `{}` or malformed reply is ignored. **Rev ≥ 31 (displays):** `displays` (list, always present, `[]` when headless) describes every connected DRM connector from `/sys/class/drm` — per entry `connector`, `width`/`height`/`refresh_hz` (the mode the compositor is driving, read via `wlr-randr` over the kiosk's Wayland socket; falls back to the EDID's preferred mode with `refresh_hz` null when the kiosk is down), `native_width`/`native_height`, `physical_mm` (`[w, h]`), `diagonal_in`, and EDID `make`/`model` — plus a flat `screen_resolution` (`"WxH"` of the first display, null when headless) for the fleet table. Nothing is cached, so a swapped monitor shows up on the next 5-minute post. **Rev ≥ 32 (update outcome):** `last_update_ok_at` (epoch of the last completed install run), `last_update_error_at` + `last_update_error` (`"rev <N> line <L>: <cmd>"`, `"rev ? reinstall exited <rc>"`, or since rev 35 `"rev ? reinstall interrupted"`; max 500 chars; both null once a later run succeeds) — see the failure-reporting note under 1. **Rev ≥ 35:** `last_update_warnings` (list of strings, always present, `[]` when the last run was clean) — the tolerated failures of the last run, see the warnings note under 1; the panel needs a field for it to be visible, otherwise it is ignored harmlessly. `wlr-randr` is apt-installed since rev 31 (before that nothing installed it — Raspberry Pi Desktop images carry it as a dependency of the `raindrop` screen tool, a Lite image does not, and the screen switch silently did nothing without it). The fetchers (`irl-update`, `irl-gateway-config`, `irl-telemetry`, `irl-screen`, and the installer's own downloads) also pin `--proto =https --tlsv1.2` whenever their URL is https, so a redirect can never downgrade to plain http (auto-relaxed for the e2e suite's localhost URLs).
8. **Scheduled reboot** (`irl-player-reboot.timer`): reboots every device Sun 04:00 local (`OnCalendar`, 30 min jitter, deliberately **no `Persistent=`**). Since rev 29 the service has `ExecCondition=/usr/local/bin/irl-netwatch --online`, so an offline device is skipped (not failed) and reboots the next Sunday it is online — no automatic reset ever reaches an offline venue. It exists because `unattended-upgrades` runs with `Automatic-Reboot false` — without a scheduled reboot a healthy device never applies a downloaded OS/kernel security update, and (before the timer fix below) never re-armed a broken updater. A device whose update timer is dead only converges on reboot; force one with `sudo systemctl start irl-player-update.service` or a power-cycle.

Other invariants:

- **The watchdog and netwatch are restarted on every installer run** (rev ≥ 34). They are endless bash loops, so a running copy keeps executing the code it started with; before rev 34 a change to either only took effect at the weekly reboot. Their state lives on disk in `/var/lib/irl-player`, so the restart is lossless. The gateway is not restarted (its `RuntimeMaxSec=1d` picks up changes within a day; a restart would drop MQTT).
- **Installer-managed scripts are written atomically** via `install_script` (temp file + `mv`, a new inode) — never `cat > /usr/local/bin/...`. The updater re-runs `install.sh` from inside the running `irl-update`; bash reads a script incrementally, so truncating and rewriting the inode a running bash holds open makes it resume at its old byte offset inside the new file and execute garbage. The rev 32 rollout did exactly that on the canary (the old updater emptied `installer.sha256` and died with a syntax error after a successful reinstall — self-healing on the next hourly run, but ugly). `irl-update` also ends with `main "$@"; exit $?` on one line. The e2e suite grows the updater mid-update and asserts a clean exit, and greps that no `cat >` write remains.
- **Never add `Persistent=` to a monotonic timer** (`OnBootSec`/`OnUnitActiveSec`, no `OnCalendar=`). On the fleet's systemd 257, `Persistent=true` on the update timer collapsed its next elapse to `infinity` once a stamp file existed (the state right after every install), silently killing the hourly re-check — devices then only updated on reboot. `Persistent=` is meaningful ONLY for `OnCalendar=` timers. Removed from the update timer; an e2e check now guards against it returning.
- **Bump `INSTALLER_REV` on every `install.sh` change** (it's the fleet-visible revision, logged by every device run and shown in the website footer).
- The website footer (`index.html`) fetches `install.sh` at runtime and regex-parses `^INSTALLER_REV=(\d+)` and `^VERSION="..."`, then HEAD-checks `packages/irl-player_<version>_<arch>.deb` (shows "package missing!" if absent). Don't change the format of those two lines. The "Guide version N" fallback text in the footer is hand-bumped when `index.html` changes.
- The whole repo is published as the website — anything committed is publicly served.
- `uninstall.sh` removes everything including `/opt/irl-gateway` (and its cached credential) and the `/etc/irl-player` state dir — which holds the canary marker, so **re-mark a test device with `sudo touch /etc/irl-player/canary` after any uninstall/reinstall** (this has been forgotten twice; the symptom is the canary deferring updates by 24 h).
- The rpi5 test device's serial is `0aa6bd2679151255` (approved in the config panel). SSH as `maz@192.168.100.249`. The e2e suite makes no host changes, so it's safe to run there (`rsync` the repo over, `sudo bash tests/run-e2e.sh`) when you need a real Linux+root+systemd environment.
- A device on the player's static "Pair this screen" page trips the freeze watchdog into a restart cycle (~every 6.5 min) — the page's "BUFFERING" animation is too small to survive grim's 1/8-scale capture. Since rev 27 the static-page brake caps the resulting reboots at one per day (they were every 2 h); the restart blinking remains. The symptom is a blinking unpaired device — re-pairing stops it.
- Uninstall/reinstall wipes the player's pairing (userdel -r removes irlplayer's home) — expect the setup QR page after a reinstall until the screen is re-paired.

## Releasing a new app version

1. Add `packages/irl-player_<newversion>_<arch>.deb` — **never reuse a version number** for different contents (devices key off `install.sh`'s hash, and apt skips same-version reinstalls).
2. In `install.sh`: bump `VERSION` and `INSTALLER_REV`.
3. Single commit, PR, merge to `main`. The canary device converges within the hour; the rest of the fleet follows `FLEET_DELAY_HOURS` later. The site footer confirms what's deployed. CI (`.github/workflows/tests.yml`) runs the e2e suite on every PR.

New architectures: add the `.deb` and extend `SUPPORTED_ARCHS`. The Raspberry-Pi model check applies to `arm64` only (CM5 passes — its device-tree model contains "Raspberry Pi"). Caveat for x86/amd64: the device serial (used by both telemetry and the gateway config fetch) is parsed from `/proc/cpuinfo`'s `Serial` line, which only exists on a Pi — on non-Pi hosts it's empty and `irl-telemetry` exits early (no token, no snapshot), so a real port needs a cross-platform serial source (e.g. `/etc/machine-id` or DMI). The `cmdline.txt` console-blanking edit is also Pi-only (harmless — missing files are skipped).
